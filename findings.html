Summary

Two symptoms were investigated in the WalkingPad → Health Connect sync (app/src/main/java/li/klass/walkingpad2hc/sync/):

  1. Huge amounts of steps posted although already posted before — always during start sync. Root cause: the baseline/catch-up logic trusted persisted counters (lastWritten) and assumptions (daily counter reset) instead of reconciling against what Health Connect actually holds. Three concrete duplication paths found; all fixed.
  2. Sync stops when the app goes to background. Two plausible causes found and fixed: the dataSync foreground-service 6-hour budget (Android 15+) and the Wi-Fi SSID gate tearing down a live MQTT connection whenever the SSID becomes unreadable (typical with the screen off). A third (OEM battery optimization) is a manual action.

Core principle of the fix

Health Connect itself — the app's own records for today — is now the source of truth for "what was already posted". Persisted markers are hints only. Where state is ambiguous, the policy prefers under-counting over duplicating: duplicates are permanent, missed steps are recovered by subsequent delta records.

New decision module

All baseline/catch-up decisions moved into a pure, fully unit-tested class CatchUpPolicy.kt (19 new test cases covering the full use-case matrix, see Use-case matrix).

Duplicate-step defects 3 critical

All three critical paths live in the baseline / catch-up logic — the branch that runs when the service starts, receives its first MQTT message (the treadmill's cumulative counter), and must decide how much of it is new. The per-message delta path (StepDeltaCalculator records) was reviewed and is correct — it was not the source of the duplicates.

D1 — Fresh baseline re-posts the full counter when Health Connect read fails

critical start sync

On a fresh baseline (no persisted lastWritten marker, e.g. first sync of the day after the old day-rollover logic, or after state loss) the old code read the app's own steps from Health Connect via HealthConnectWriter.ownStepsSummary(). That method returns null on any exception. The old code treated null as "Health Connect is empty" → alreadyThere = 0 → wrote the entire day counter again.

Health Connect reads are exactly the kind of call that fails right after process start (client not yet available, binder contention right after startForegroundService). That matches the reported pattern: "always during start sync".

// old behavior (BaselineSet branch)
val own = writer.ownStepsSummary()          // null on ANY exception
val alreadyThere = own?.total ?: 0          // read failure == empty day
writeSteps(..., steps - alreadyThere)       // full counter re-posted

Fix: a failed reconciliation read now defers the write (CatchUpPolicy final guard: never write without a successful read). The decision is parked as a pending record and retried with the next MQTT message.

D2 — Day rollover assumed the treadmill counter resets at midnight

critical first start of day

The old !sameDay branch wrote the full counter value whenever the last written marker was from a previous day. That is only correct if the treadmill's counter resets across midnight. If the treadmill stays powered (or its counter is cumulative), the MQTT counter keeps counting — and the sync re-posted everything already posted as one giant record. This is the prime suspect for "huge amounts of steps" on the first sync of the day.

Fix: across days the policy compares the incoming counter against max(lastWritten.endSteps, lastSeen.steps). A counter at or above yesterday's level is treated as a continuation — only the excess is written; a lower value is treated as a reset and reconciled against today's own Health Connect records.

D3 — Same-day catch-up trusted the persisted marker alone

warning restart kill window

On restart, the old same-day catch-up computed the gap purely from the persisted lastWritten marker. The marker is written after a successful insertRecords — if the process dies in between (or the DataStore persist fails), the marker lags behind what Health Connect actually holds, and the restart re-writes the already-written gap. The clientRecordId dedupe does not help here: the catch-up computes a new start/end range, producing a new ID.

Fix: catch-up coverage is now max(marker, own Health Connect total for today) — the actual records cap the marker.

D4 — Pending-record retry checked only the marker, not Health Connect

warning retry path

pendingCovered() decided "already written" solely via SyncStatePolicy.isCoveredByLastWritten. Same lag window as D3: a pending record could be re-written although Health Connect already holds it (mitigated only when the recomputed range produced the identical clientRecordId).

Fix: the retry path now also reconciles against the app's own Health Connect records before re-writing.

D5 — Delta path wrote implausible counter jumps confirmed on device treadmill reboot

Confirmed by device log (13:06): after an app restart the broker's retained message "stepsTotal": 0 set the in-memory baseline to 0; 32 seconds later the treadmill published stepsTotal: 11295 (its cumulative counter — it had rebooted and resumed at the accumulated total). The in-session delta path computed 11295 − 0 and wrote it blindly as one record over 32 seconds (353 steps/s) — all of it already posted before the reset. The baseline path reconciles against Health Connect; the delta path was the last path trusting the counter unconditionally. Superseded by D6: retained snapshots now always force reconciliation of the next delta.

D6 — Retained snapshot poisoned the calculator baseline confirmed on device reconnect replay

Confirmed by device log (Oct 28, 15:09): the broker replays its retained message on every reconnect. After a treadmill reboot the retained snapshot is "stepsTotal": 0 — it set the calculator's in-memory baseline to 0 (the catch-up path correctly wrote nothing for the snapshot itself). Hours later, the next live message arrived with the accumulated counter 8867; the delta path computed 8867 − 0 and wrote the full amount as one record over a 3-hour window. That window is slow enough (~48 steps/min) to pass the D5 rate guard — the rate check only catches fast jumps, not a slow-poisoned baseline.

Fix: every retained message now arms a flag; the next delta is routed through the same Health Connect reconciliation as baselines (covered = max(lastWritten marker, own records)) instead of being written blindly. Retained snapshots can also no longer produce blind Records themselves.

Context: why clientRecordId alone didn't save us

Every written record carries clientRecordId = "wp2hc-<start>-<end>-<count>", so an exact retry (same range) is upserted by Health Connect instead of duplicated. But all four defect paths computed a different range or count than the original write — new ID, real duplicate. The dedupe remains useful for exact retries (e.g. timeout-after-success), but it cannot be the only line of defense.

Background stops 1 critical

The second symptom — sync stopping while the app is in the background — has two code-level causes (both fixed) and one environmental cause (manual action).

B1 — dataSync foreground service is time-limited on Android 15+

critical targetSdk 37

Since Android 15, foreground services of type dataSync (and mediaProcessing) get a 6-hour runtime budget per 24 hours. When exhausted, the system calls ForegroundServiceTypeTimeoutException-style onTimeout() and the service must stop — our StepSyncService.handleTimeout() sets an error and calls stopSelf(). Foregrounding the app resets the budget, which is why the sync "magically works again" when the app is opened — matching the reported "stops in background".

Fix v2 (after the first attempt crashed on-device): the health type additionally requires a qualifying permission — ACTIVITY_RECOGNITION, HIGH_SAMPLING_RATE_SENSORS, or one of seven specific health READ permissions. The first attempt gated on WRITE_STEPS, which the system explicitly does not count, so startForeground threw SecurityException and the app crashed on start. The gate now mirrors the system's list exactly (ForegroundServiceTypePolicy, unit-tested), MainActivity requests ACTIVITY_RECOGNITION at runtime (Android 10+), and until it is granted the service safely falls back to dataSync — the pre-existing, valid type. Manifest updated with FOREGROUND_SERVICE_HEALTH + ACTIVITY_RECOGNITION permissions and the new service type. Verified against the official documentation: developer.android.com/develop/background-work/services/fgs/timeout — only dataSync and mediaProcessing are limited; health is not.

B2 — Wi-Fi gate disconnected a working MQTT connection on unreadable SSID

warning screen off

evaluateGate() called disconnectMqtt() whenever the gate reported a reason — including "Wi-Fi SSID unavailable". Android frequently fails to deliver the SSID with the screen off or in the background (and always after a process restart, where the cached lastKnownSsid is empty). Result: a perfectly healthy MQTT connection on the right network was torn down, and the service sat in WAITING_FOR_NETWORK until the screen came back on.

Fix: when the gate is blocked but an MQTT connection is already established, the connection is kept — a live connection is proof of the right network. The gate only steers connection attempts, never tears down an established one.

B3 — OEM battery optimization / aggressive app killers manual action

Some vendors kill background services regardless of foreground-service type. This cannot be fixed purely in code: disable battery optimization for walkingpad2hc (Settings → Apps → walkingpad2hc → Battery → Unrestricted), and exempt it from any vendor-specific "battery saver" that terminates background apps. If stops persist on a specific device after the fixes above, this is the first suspect — check adb logcat for the process being killed without a service lifecycle event.

Known limitations & caveats

  • Ambiguity is resolved toward under-counting. If the treadmill counter resets and the user has already walked past yesterday's total before the first sync of the day, the new value can exceed max(lastWritten, lastSeen) and is interpreted as a continuation — the excess is written, but steps between the reset point and the old maximum are not recoverable. This is deliberate: a wrong guess toward "reset" would duplicate; the chosen bias never duplicates and misses only in this corner case.
  • Mid-day counter reset + restart is conservative. After a mid-day reset, catch-up reconciles against today's own HC records; if markers are unavailable it defers rather than guessing. May under-count until the next in-session delta records flow normally.
  • Monotonic-counter assumption. The day-rollover logic assumes the MQTT counter is a per-day (or at least non-decreasing during a day) counter. If the source publishes per-session counters, the continuation interpretation degrades to under-counting, never duplication.
  • The in-app "steps today" metric aggregates all sources. HealthConnectWriter.stepsToday() counts every app's steps for today — display only, never used for sync decisions.
  • No persistent MQTT session. The client uses a clean session (random client ID); messages published while disconnected are lost. Catch-up therefore relies on the retained/current counter value — another reason the reconciliation-based catch-up matters.
  • The delta Record path was left unchanged — it was reviewed and is correct (epoch-based ranges from the last recorded end time).
  • Device-dependent behavior cannot be unit-tested: HC read/write failures, FGS type selection, and SSID readability need the on-device smoke test above.
